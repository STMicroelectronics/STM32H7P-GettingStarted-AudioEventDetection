HAL CRYP migration: List of applicable concepts ¶

This section provides information about the HAL CRYP applicable architecture concepts.

Concepts for CRYP ¶

Concept

Description

Split legacy HAL_PPP_Init into Init (build handle object) and config (apply configuration)

Provide a separate configuration per algorithm with the parameters strictly required for the given algorithm.

Remove Init structure from handle and convert Init structure into configuration one

The init structure is removed from the handle and converted into set configuration per algorithm function.

Rename handle structure

The handle structure is renamed to hal_aes_handle_t for aes peripheral and hal_cryp_handle_t for aes peripheral.

Rename unitary init structures

The structure CRYP_InitTypeDef no longer available, they have to be replaced by hal_aes_gcm_config_t , hal_aes_ccm_config_t``for aes peripheral and ``hal_cryp_gcm_config_t , hal_cryp_ccm_config_t for cryp peripheral.

Remove MspInit and MspDeInit callbacks

MspInit and MspDeInit are no longer available. They must be replaced by a user sequence to initializes and configures the CRYP or AES.

Add unitary configuration APIs

New configuration APIs are available to set AES features.

Remove __HAL_LINKDMA generic macro and provide a dedicated API per DMA field​

The __HAL_LINKDMA macro is removed, and new HAL_AES_SetInDMA and HAL_AES_SetOutDMA functions for AES peripheral and HAL_CRYP_SetInDMA and HAL_CRYP_SetOutDMA functions for CRYP peripheral are provided for linking a HAL AES handle to a HAL DMA handle.

Add HAL User Data Set/Get APIs

Add Set/Get User Data functions HAL_AES_SetUserData , HAL_AES_GetUserData``for AES peripheral and ``HAL_CRYP_SetUserData and HAL_CRYP_GetUserData functions for CRYP peripheral.

Split Global Register callback API to one register API per callback and remove unregister callback API

The callback registration is handled by specific functions for each CRYP event.

These functions are used to register callback functions for different AES events.

Keep Global HAL PPP IRQ Handler and Provide Specialized HAL PPP IRQ Handlers for Individual scope

keep IRQ Handler without split.

Use a compilation flag per algorithm to reduce the footprint.

Keep common error handling ( These errors are blocking).

Revise and optimize the HAL state machine.

The CRYP and AES state machine should be used to track the operational states and transitions of the peripheral, such as HAL_AES_STATE_RESET , HAL_AES_STATE_INIT , HAL_AES_STATE_IDLE , HAL_AES_STATE_ACTIVE , HAL_AES_STATE_SUSPENDED for AES peripheral and HAL_CRYP_STATE_RESET , HAL_CRYP_STATE_INIT , HAL_CRYP_STATE_IDLE , HAL_CRYP_STATE_ACTIVE , HAL_CRYP_STATE_SUSPENDED for CRYP peripheral.

Revise and optimize the status return of HAL APIs.

Update CRYP and AES functions to return HAL_INVALID_PARAM in case of NULL p_config structure pointer HAL_ERROR in case of error , HAL_TIMEOUT in case of user timeout , HAL_BUSY in case of process ongoing and HAL_OK in case of operation completed successfully.

Revise and optimize HAL error management.

Involves redesigning the error handling mechanisms within the HAL to improve the detection, reporting, and handling of errors. This rework aims to provide more detailed and consistent error code reporting.

Remove single or double underscore prefixes from any define or macro, as this is not allowed per the C standard.

All underscore prefixes in CRYP and AES are removed.

Replace the “TypeDef” part of every typedef with “_t”.

All TypeDef part in CRYP and AES are removed and replaced by _t .

Replace big macros with inline functions for consistency.

Use inline functions instead of large macros for the CRYP and AES helps maintain code consistency, improve readability, and benefit from compiler optimizations. Inline functions also offer better support for debugging and strict type management, thereby reducing the risk of errors.

Replace non-modifiable pointers with const keywords.

Adding const keywords to non-modifiable pointers ensures that either the pointer itself or the data it points to cannot be modified. This enhances code safety and readability and using const, you prevent unintended modifications and make your code more robust and maintainable.

Replace parameter and state checks with assertions.

The parameters and state are checked using ASSERT_DBG_STATE and ASSERT_DBG_PARAM macro

Merge HAL extension files with common ones and remove the EX prefix from APIs.

Only one HAL AES header file now is available and all the macro,define,function ,… in hal_aes_ex.h or hal_cryp_ex.h are adapted and mergerd in hal_aes.h or hal_cryp.h

Replace the assert_param macro with ASSERT_DBG_PARAM, controlled by the USE_ASSERT_DBG_PARAM conditional.

Introduce a conditional compilation flag USE_ASSERT_DBG_PARAM to enable or disable debug parameter assertions, allowing for flexible debugging and validation.

Add ASSERT_DBG_STATE macro controlled by USE_ASSERT_DBG_STATE conditional.

Introduce a conditional compilation flag USE_ASSERT_DBG_STATE to enable or disable debug parameter assertions, allowing for flexible debugging and validation.

Replace Finite Parameter Defines (Including PPP Instances) with Enum Types at HAL Levels.

Convert finite parameters, (including AES instances) into enumerated types (enums) at the HAL level. This improves code readability, maintainability, and type safety.

Add HAL_PPP Prefix to All HAL Peripheral APIs (Defines, Macros, Types, and Functions).

All HAL AES/CRYP enums and struct start with hal_aes for AES peripheral and hal_aes for CRYP peripheral.

Other HAL CRYP changes ¶

Concept

Consideration

CRYP driver implementation depends on the available peripherals:

The main issue on Cube 1. x:

One driver HAL AES for all families with different hardware instances ( AES, SAES, AES, and AES2(next products) )

Provide a dedicated HAL driver for each peripheral:

HAL AES driver: specific to address AES and SAES peripheral.

HAL CRYP driver: specific to address CRYP peripheral.

Rework Suspend/Resume mechanism to avoid saving context within the handle.

Remove the suspend resume context parameters from the handle in order to gain footprint.

Use a dedicated “save context” structure with dedicated Save/restore context APIs.

Factorize the context structure to keep only the required parameters.

Use flags compilation to enable supporting the possible algorithms.

This proposition will lead to a significant optimization and simplification of the code.

A new format of user data: the buffers to be a void* type and the size in bytes.

The user data endianness and alignment constraint remains as HAL and will be explained further in the driver documentation.

For the migration part, the user buffers provided in HAL1 applications remain valid for HAL2 ones.

The user must provide aligned buffers, the HAL driver will check the alignment with assert and then use 32bits pointer access for the whole provided buffer.

The user must be careful about his data endianness and swap mode configuration:

Data must be provided in big-endian when it’s not swapped.

When data are provided in little-endian, the user must configure the swap mode.

The padding will be maintained at the word level so that the driver will only pad the missing entire words within a block with zeros ( 4 words are required to feed the data input register).

Rework the key configuration and setting.

Split the key configuration from the global configuration.
